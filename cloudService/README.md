# Cloud Storage Service

RESTful API для облачного хранения файлов с поддержкой авторизации, управления файлами и мягкого удаления (soft delete). Проект разработан в рамках дипломной работы с применением методологии TDD, контейнеризации и интеграционного тестирования.

## Архитектура приложения

Приложение построено по классической трёхуровневой архитектуре:
1. **Reverse Proxy (Nginx)**: единая точка входа, обработка CORS, проксирование запросов.
2. **Backend (Spring Boot)**: бизнес-логика, авторизация, валидация, работа с файловой системой.
3. **Data Layer**:
    - **PostgreSQL**: хранение метаданных пользователей и файлов.
    - **File System**: физическое хранение бинарных данных файлов.

```text
┌─────────────┐      HTTP/REST      ┌─────────────┐      JDBC      ┌─────────────┐
│   Frontend  │ ──────────────────► │   Nginx     │ ─────────────► │ PostgreSQL  │
│  (Vue.js)   │ ◄────────────────── │  (:80)      │                │   (:5432)   │
└─────────────┘                     └──────┬──────┘                └─────────────┘
                                           │
                                           ▼
                                    ┌─────────────┐
                                    │ Spring Boot │ ───────────────► File System
                                    │   (:8080)   │                  (./app/files)
                                    └─────────────┘
```

## TDD (Test-Driven Development)

Ключевые компоненты приложения разрабатывались с использованием методологии TDD. В качестве примера можно привести реализацию метода авторизации `AuthService.login()`:

1. **Сначала написаны тесты** (`AuthServiceTest.java`):
    - Успешный вход с валидными данными.
    - Ошибка при неверном логине.
    - Ошибка при неверном пароле.
2. **Затем написана реализация**, минимально необходимая для прохождения тестов.
3. **Рефакторинг**: код был очищен, добавлено логирование и аннотация `@Transactional`.

Это гарантирует, что бизнес-логика авторизации покрыта тестами с первого дня и защищена от регрессии.

## Быстрый старт

Для запуска приложения требуется установленный **Docker** и **Docker Compose**.

1. Клонируйте репозиторий:
   ```bash
   git clone <url-репозитория>
   cd cloud-service
   ```

2. Запустите все сервисы (Backend, PostgreSQL, Nginx) в фоновом режиме:
   ```bash
   docker-compose up -d --build
   ```

3. Проверьте статус контейнеров:
   ```bash
   docker-compose ps
   ```
   *Все сервисы должны быть в статусе `running` (или `healthy` для PostgreSQL).*

4. API будет доступно по адресу: `http://localhost:80` (через Nginx) или `http://localhost:8080` (напрямую к Backend).

## 📡 API Endpoints

Базовый путь: `/cloud`

| Метод | Путь | Описание | Требуется `auth-token` |
|-------|------|----------|------------------------|
| `POST` | `/login` | Авторизация пользователя | Нет |
| `POST` | `/logout` | Выход из системы (аннулирование токена) | Да |
| `POST` | `/file?filename=...` | Загрузка файла (`multipart/form-data`) | Да |
| `GET` | `/file?filename=...` | Скачивание файла | Да |
| `PUT` | `/file?filename=...` | Переименование файла (JSON body: `{"name": "new"}`) | Да |
| `DELETE` | `/file?filename=...` | Мягкое удаление файла (soft delete) | Да |
| `GET` | `/list?limit=...` | Получение списка файлов пользователя | Да |

### Формат ошибок
Все ошибки возвращаются в едином формате (HTTP 400, 401, 500):
```json
{
  "message": "Описание ошибки",
  "id": 0
}
```

## Особенности реализации

- **Soft Delete**: При удалении файла запись не удаляется из БД физически. Используется аннотация Hibernate `@SQLDelete` для выполнения `UPDATE files SET deleted = true`, а аннотация `@Where(clause = "deleted = false")` автоматически фильтрует такие записи во всех обычных запросах.
- **Безопасность**:
    - Docker-образ собирается в multi-stage режиме и запускается от имени непривилегированного пользователя (`appuser`).
    - Реализована защита от Directory Traversal при работе с файловой системой.
    - Изоляция данных: пользователи видят только свои файлы.
- **CORS**: Настроен на уровне Nginx для безопасного взаимодействия с Frontend-приложением.

## Тестирование

Проект покрыт двумя уровнями тестов:

1. **Unit-тесты (Mockito)**: Проверка бизнес-логики сервисов изолированно от внешних зависимостей.
2. **Интеграционные тесты (Testcontainers)**: Поднимают реальный контейнер PostgreSQL для проверки корректности SQL-запросов, транзакций и работы аннотаций JPA.

Для запуска всех тестов выполните:
```bash
./mvnw clean test
```
